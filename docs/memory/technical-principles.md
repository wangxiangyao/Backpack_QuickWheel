# 源码驱动开发原则 - 详细版

## 🔥 核心原则阐述

### 1. 源码驱动开发原则 【铁律】

**为什么必须源码驱动？**
- Unity系统参数含义经常与直觉相反
- 官方API性能和兼容性最优
- 避免重复造轮子和隐藏陷阱

**实施标准流程**:
```
问题复现 → 查找GameSource/Duckov/源码 → 分析参数含义 →
基于源码实现 → 验证效果 → 记录最佳实践
```

**绝对禁止的行为**:
- ❌ 基于参数名称猜测功能
- ❌ 基于其他游戏经验实现功能
- ❌ 不看源码就实现复杂功能
- ❌ 忽略官方API而自定义实现

### 2. 官方API优先原则

**优先级排序**:
1. **官方API** - 游戏提供的标准接口
2. **官方模式** - 源码中推荐的做法
3. **Coop-Mod参考** - 已验证的第三方实现
4. **自定义实现** - 仅在前三者都不可用时

**官方API优势**:
- 性能最优（底层优化）
- 兼容性最好（跟随游戏版本）
- 维护成本最低
- 避免重复工作

### 3. 简洁性原则

**复杂度警示**:
- 协程 > 简单方法调用
- 反射 > 直接访问
- 多层抽象 > 简单实现
- 自定义系统 > 官方API

**简洁性检查清单**:
- [ ] 是否有更简单的官方API？
- [ ] 是否真的需要协程？
- [ ] 反射是否可以用直接访问替代？
- [ ] 抽象层是否过多？

## ⚡ 参数验证铁律

### 标准验证流程

**步骤1: 源码确认**
- 查看参数定义和默认值
- 理解参数的真实含义
- 确认取值范围和边界

**步骤2: 小范围测试**
```csharp
// 测试不同参数值
PopText(text, 1f);    // 很慢
PopText(text, 10f);   // 默认速度
PopText(text, 50f);   // 很快
PopText(text, 100f);  // 极快
```

**步骤3: 效果记录**
- 记录不同参数的视觉效果
- 确定最优参数值
- 在代码中添加注释说明

**步骤4: 文档化**
- 记录到记忆文件
- 更新相关文档
- 分享给团队成员

### 参数误解案例分析

**气泡速度参数**:
- **常见误解**: speed越小越快
- **源码真相**: speed越大越快（控制动画速度）
- **错误用法**: `PopText(text, 0.1f)` // 实际是超级慢
- **正确用法**: `PopText(text, 50f)`  // 5倍速
