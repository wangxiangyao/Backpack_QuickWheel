# 背包配件与轮盘快选 | Backpack Attachments & Quick Wheel

一个为《逃离鸭科夫》游戏开发的功能性 Mod，为玩家的背包系统增加了配件插槽、智能快捷键和创新的轮盘选择界面。

## ✨ 核心功能

### 1. 模块化背包配件系统
- **12个独特配件**：从基础网兜到高级战术包，满足不同背包等级的扩展需求
- **智能插槽限制**：每个插槽通过标签（tag）系统控制接收的物品类型
- **递归容器支持**：配件中可以继续放置配件，实现多层级的物品组织
- **持久化保存**：所有配件配置自动保存，游戏重启后自动恢复

### 2. 智能快捷键系统
- **4个独立快捷键**（默认：3、4、5、6）用于快速使用医疗、兴奋剂、食物和爆炸物
- **背包递归搜索**：自动搜索背包→所有配件中的物品，无需手动分类
- **物品分类管理**：系统自动按类型组织，支持医疗、兴奋剂、食物、爆炸物四大类
- **背包装备感知**：仅在背包装备时激活，自动应对配件变化

### 3. 九宫格轮盘快速选择
- **长按快捷键显示轮盘**：0.2秒阈值，快速显示8格轮盘菜单
- **矢量方向选择**：通过鼠标移动方向智能选中物品，比悬停更高效
- **布局持久化**：用户调整的物品位置自动保存，游戏重启后恢复原布局
- **实时聚焦反馈**：选中格子放大+变亮，清晰的视觉反馈

### 4. 直观的UI可视化
- **插槽信息面板**：Hover 配件时显示所有插槽内容、容量和限制标签
- **点击详情查看**：点击配件物品跳转到详情面板，支持直接拖拽调整
- **圆孔高亮反馈**：拖拽物品时，所有可接收该物品的槽位自动高亮（绿色）
- **多行indicator布局**：支持超过8个插槽的背包（如行军背包的10个插槽）正常显示

## 📦 使用指南

### 安装
1. 将 `Backpack_QuickWheel` 文件夹放入游戏的 `Mods` 目录
2. 文件结构：
   ```
   Escape from Duckov/
   └── Duckov_Data/
       └── Mods/
           └── Backpack_QuickWheel/
               ├── Backpack_QuickWheel.dll
               ├── Backpack_QuickWheel.pdb
               └── [其他编译输出文件]
   ```

3. 启动游戏，配件自动加载并应用到所有背包

## 🛠️ 开发者指南

### 环境要求

- **.NET SDK 6.0+** 或 Visual Studio 2022
- **游戏源码** 放在 `GameSource/` 目录（用于参考，不参与编译）

### 构建项目

```bash
# 编译项目（自动输出到游戏 Mods 目录）
dotnet build Backpack_QuickWheel.csproj -c Release

# 或在 Visual Studio 中直接编译
# Output: Duckov_Data/Mods/Backpack_QuickWheel/
```

输出路径配置在 `.csproj` 文件中，自动将编译结果复制到游戏目录。

### 关键技术细节

- **Harmony Patching**：使用 Harmony 2.4.1 无侵入式修改游戏方法
- **反射技术**：访问游戏私有字段的 `ReflectionExtensions` 辅助类
- **事件系统**：通过游戏的事件系统感知背包变化
- **资源嵌入**：将图片资源嵌入 DLL，运行时动态加载
- **Item类使用注意**：详见 `CLAUDE.md` 的"Item类使用注意事项"部分

### 添加新配件

1. 在 `BackpackModConfig.cs` 的 `AttachmentItemConfigs` 中添加条目
2. 选择唯一的 TypeID（349100-349999 范围）
3. 提供中英文本地化文本
4. 在 `.csproj` 中嵌入配件图标：
   ```xml
   <EmbeddedResource Include="Textures/YourItemName.png" />
   ```
5. 为新配件图标指定合适的品质等级（Green/Blue/Purple/Orange/Red）

详细的开发规范请参见 `docs/DEVELOPMENT-开发指南.md`。

## 🤖 开发过程：人工智能与人工的合作

这个 Mod 的开发展示了人工智能和人类在复杂系统设计中的高效协作模式。

### 协作模式

**人类的关键作用**：
- 理解游戏底层系统的复杂性（物品层级、事件触发顺序等）
- 诊断性能瓶颈和逻辑缺陷（通过深入的系统分析）
- 指导 AI 检查游戏源码，梳理问题的真正根源
- 做出高层级的架构决策（数据流、缓存策略等）

**AI 的关键作用**：
- 实现具体的代码解决方案
- 生成和维护补丁逻辑（Harmony patches）
- 自动化繁琐的任务（文件重组、文档整理）
- 提供快速的多角度问题分析

### 案例1：钥匙无法在配件中使用

**问题现象**：玩家把钥匙放入配件的插槽，接近上锁的箱子仍显示"需要钥匙"，无法打开。

**人类的诊断过程**：
1. 意识到问题在于物品搜索逻辑
2. 查阅游戏源码发现 `Inventory` 链条在物品放入 `Slots` 后被断开
3. 指出应该从 `Character.CharacterItem.Slots` 开始搜索，而非 `Inventory`
4. 强调通过 GameObject 的 `transform.parent` 关系判断物品位置更可靠

**AI 的实现过程**：
- 创建 `InteractableTryGetRequiredItemPatch.cs` 拦截搜索流程
- 实现递归函数 `SearchInSlots()` 遍历嵌套的配件和插槽
- 正确处理三层结构：Character.Slots → Attachment.Slots → NestedItem

**关键发现**：
- ❌ 错误假设：`Item.InInventory` 能判断物品位置（不可靠，链条已断）
- ✅ 正确方向：通过物理层级（GameObject transform）查找物品所属背包
- 📌 经验：对游戏系统的假设必须通过源码验证，不能靠猜测

### 案例2：圆孔拖拽高亮导致性能下降

**问题现象**：拖拽物品时，游戏出现明显卡顿（0.3秒冻屏），原因是圆孔高亮判断的性能问题。

**人类的诊断过程**：
1. 通过日志发现：每次拖拽触发 40 个 indicator 的判断
2. 分析发现：40 个 `CanPlug()` 调用在同一帧执行，导致 CPU 占用 100%
3. 提出解决方向：**将判断分散到多帧执行**
4. 建议架构：**使用规则缓存而非重复计算**

**AI 的实现过程**：
- 创建 `SlotIndicatorCacheManager.cs` 在 Setup 时收集所有规则
- 实现多帧 Coroutine：每帧仅处理 2 个 indicator，共 20 帧完成
- 添加 `Setup_Postfix` 计算每个 indicator 的限制规则并分类
- 优化参数：`itemsPerFrame = 2` 实现流畅度和响应速度的平衡

**性能对比**：
| 指标 | 优化前 | 优化后 | 改善 |
|------|-------|-------|------|
| 每帧事件订阅 | 40 个 | 1 个 | **96% 减少** |
| 拖拽首帧卡顿 | 0.3秒 | 0ms | **完全消除** |
| 总处理时间 | 单帧 | 20帧 | **分散执行** |

**关键发现**：
- ❌ 错误方向：盲目优化渲染层（SetAllDirty → SetMaterialDirty）
- ✅ 正确方向：通过日志找到真实瓶颈（单帧任务过多）
- 📌 经验：性能问题必须通过数据驱动分析，不能靠感觉优化

### 开发中的AI指导原则

1. **总是检查游戏源码** - 不要基于假设实现，必须验证官方行为
2. **问题分析优于代码修改** - 先理解问题根源，再确定解决方案
3. **通过日志和数据决策** - 性能优化必须有客观的性能指标支持
4. **架构决策由人类确定** - 数据流、缓存策略等决策权在人类
5. **及时验证假设** - 开发中如果有疑问，立即查阅源码而非继续推测
