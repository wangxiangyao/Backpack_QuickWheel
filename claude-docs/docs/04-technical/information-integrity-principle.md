# 信息完整性原则 - 究极准则

## 🔥 **最高优先级：信息完整性原则**

### 核心原则
**绝对禁止基于假设做决策，必须暴露信息缺口并寻求确认**

### 触发条件（必须停止的情况）
1. **找不到类/方法定义**
   - ItemFilter, RandomContainer, OnQuackInput等
   - 反射时找不到目标字段或方法

2. **方法实现被编译隐藏**
   - async状态机，运行时生成的方法
   - IL2CPP编译后的方法
   - 动态生成的委托

3. **缺少关键配置文件**
   - 掉落表、商店配置、输入映射
   - 资源文件、预制体配置
   - 任何影响核心逻辑的配置

4. **任何需要假设才能继续的情况**
   - "我猜这个可能是..."
   - "根据经验应该是..."
   - "一般这种情况会..."

## 🔍 **自检三连问（每次思考前必须问自己）**

### 1. 我是否基于假设在思考？
- 检查我的推理链条
- 确认每一步都有依据
- 识别任何基于经验或直觉的跳跃

### 2. 我是否暴露了信息缺口？
- 明确指出我不知道什么
- 告诉用户需要什么信息
- 描述信息缺口对问题的影响

### 3. 我是否问了用户确认？
- 寻求具体的确认
- 询问缺失的定义或配置
- 请求澄清模糊的地方

## ✅ **正确的工作流程**

### 允许猜测（探索阶段）
```
我观察到OnDash这个方法名，根据常见的游戏开发模式，
我猜测OnDash可能对应某个功能键（可能是F10或Shift+F）。
```

### 暴露信息缺口（分析阶段）
```
但是我在源码中没有找到OnDash具体对应哪个按键的映射。
我需要确认：OnDash实际对应键盘上的哪个按键？
```

### 寻求确认（决策阶段）
```
请确认OnDash对应的按键，然后我再决定如何实现热键拦截。
```

### 基于确认信息行动（实施阶段）
```
你确认OnDash对应F10，我现在实现OnDash的Harmony补丁。
```

## ❌ **错误的思维模式**

### 直接基于假设行动
```
错误：我认为OnDash可能对应F10，直接实现OnDash补丁。
结果：补丁了错误的方法，浪费时间。
```

### 隐含假设
```
错误：Tag应该有个name属性，我直接使用tag.name。
结果：运行时发现Tag类没有name属性，崩溃。
```

### 不暴露信息缺口
```
错误：找不到LootBoxLoader的定义，但我觉得它应该有这些字段。
结果：基于错误的理解实现了不完整的功能。
```

## 🎯 **实际应用案例**

### 案例1：LootBox调试系统
❌ **错误做法**：
- "我猜OnDash对应F10，直接实现OnDash补丁"

✅ **正确做法**：
- "我需要找一个方法来触发调试。我观察到有OnDash、OnQuackInput等方法"
- "但我不确定它们对应哪个按键。我应该用哪个方法来触发调试功能？"
- "你确认用快捷键8，我现在实现OnShortCutInput8的补丁"

### 案例2：语音轮盘系统
❌ **错误做法**：
- "OnQuackInput看起来像是Quack输入，直接补丁它"

✅ **正确做法**：
- "我发现OnQuackInput在源码中找不到，但你的语音轮盘成功补丁了它"
- "请问OnQuackInput是怎么工作的？为什么能补丁不存在的方法？"
- "我学习你的模式来实现调试功能"

## 🔥 **强化记忆机制**

### 每次回复前自检
1. 停下来，问自己三个问题
2. 如果发现任何假设，立即停止
3. 暴露信息缺口，寻求确认

### 复盘机制
- 每次完成任务后，回顾是否有基于假设的地方
- 记录成功的"暴露缺口→寻求确认"案例
- 分析错误，强化正确模式

### 项目记忆强化
- 在项目文档中反复强调这个原则
- 用具体案例说明正确和错误的做法
- 将此原则提升到"究极准则"的高度

## 📋 **检查清单**

在开始任何技术分析或实现前，检查：
- [ ] 我是否知道所有相关的类和方法定义？
- [ ] 我是否理解了所有参数的含义？
- [ ] 我是否暴露了任何不确定的地方？
- [ ] 我是否问了用户确认关键信息？

如果任何一项答案是否定的，**立即停止**并寻求澄清。
